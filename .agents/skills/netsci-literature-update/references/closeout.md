# 收尾与条件发布

在本轮可完成的取证和审读结束后阅读。下列仓库路径均相对实际根目录。

## 三类交付与覆盖说明

以正式日志最新有效判断为准，生成可追溯分类清单；不要创造新的科学类别去取代现有 `core`、`transferable_application`、`excluded`、`review`、`deferred_unassessed`。

| 交付 | 必须说明 |
|---|---|
| 已分类文献 | 纳入与排除、DOI／题名／期刊、简短依据及正式记录入口；纳入另给主题，特殊编辑属性保留 |
| 待人工 review | 已有材料、具体科学边界争议、AI建议和需要用户作出的决定；不把全部已判断文章再次交给用户 |
| 待人工补资料 | DOI／题名、缺少的必要摘要或元数据、已试渠道及失败、明确来源链接和用户最小补充动作 |

这是面向用户的工作队列，不是把全部 `review` 强行映射为科学争议：已读但缺关键日期或材料的 `review` 应进入补资料清单。限流未启动仍是未审读，不称为官方无摘要。两个方面均有问题时交叉注明同一 DOI，汇总按唯一 DOI 计数。机器尚能安全解决的项目先自行处理，不为省事交给用户。

从候选、状态和覆盖联合核对总数，不能遗漏未产生 assessment 的记录。定窗不明、出窗候选和重复观察单独解释，不混进已审文献计数。整刊访问失败、分页截断、无下界守卫等即使没有已知 DOI 也列为覆盖阻塞；正常“截至读取时刻”的限制与尚未完成的枚举区分。

结果详情按需写入固定的 `.private/work/<run-id>/exports/review.json` 和 `review.md`，来自正式日志并注明派生属性，不含完整摘要。简短的本轮 `README.md` 留在正式目录，说明范围、分类统计、覆盖状态、必要限制和记录入口；AI须核对叙述，不把程序成功写成科学或覆盖保证。不要为三类交付另建三套正式结果文件。

若有任一人工待办、未审读项或覆盖／技术阻塞，报告具体问题后暂停本轮发布。不删除困难记录、不将延期改为排除、不修改上次有效网站来制造完成。收到回复后恢复原轮；若已封存则建立明确复议。

## 准备发布依据

先读 `docs/publication.md`。没有人工待办仍须补齐纳入者作者、身份／日期／类型证据，以及 `config/publication-notes.json` 的中英文短说明和主题。作者使用 `collect_authors.py --run ...`；已有记录用 `--resume`，只有明确重核时才指定 `--refresh-doi`。

`publication.json` 是选择已存在依据，不是生成新的判断。当前没有统一生成 CLI，不能虚构 `seal` 或 `finalize` 命令。使用 `scripts/publication_view.py` 与 `scripts/report_io.py` 现有函数计算引用和哈希，再用现有发布器验证；哈希不可手填或从别轮复制。

普通无复议轮的清单按当前 `FlatPublicationView` 格式准备：

- `version` 为 `flat-publication-1`。
- `inventory` 由未封存轮的 `screen_candidates.Workflow` 经 `verify_assessments`、`source_reference` 得到。
- `revisions` 为明确的空列表；存在复议时必须按真实依赖顺序声明来源、mode 和 targets，不能假装无复议，也不能选“最新目录”代替明确选择。
- `authors.file` 为 `author-metadata.json`；`metadata_sha256` 为解析后 JSON 的 `run_inputs.digest`。
- `authors.audit` 指向实际保存匹配 `author_metadata_completed` 事件的日志，使用仓库相对 `path` 和 `report_io.file_sha`；普通新轮通常是自己的 screening log，不照抄历史 ZIP 引用。
- 有独立补证时按实际 `publication-evidence.json` 与内容哈希绑定；迁移映射 `evidence_paths` 只在确实迁移时需要。

先在私有工作目录准备草稿，确认所有应追加的正式事件已经保存，再最后写入本轮 `publication.json`。写入后 CLI 将该轮视为封存，不得提前创建空清单当占位符。随后使用 `publication_workflow` 验证。验证失败须修复新清单或补齐真实工作，不能篡改旧事件／解除既有封存。

更新发布选择时保留已有有效轮，明确新增窗口；`config/release.json` 中各清单按最终文件字节 SHA-256 绑定。发布器要求各刊窗口连续；历史补采若产生空档、重叠冲突或接收稿转正式发表冲突，不偷偷删掉旧轮或放宽校验，报告需要解决的范围。更换原已发布依据须有明确修订链。

## 发布门槛与执行

根据用户确认的项目条件授权，主动请求执行的常规文献更新在所有门槛通过后，可以继续提交、推送到既有发布分支并验证上线，无需再次询问选文。仅解释、演练、仅采集／预览或用户禁止推送时不适用。不是通用部署权限，不含改 CI、DNS、科学规则、付费服务或定时任务；正常工具审批不能绕过。

1. 审查两个人工队列、未审读／活跃状态和整刊覆盖；核对冻结输入与候选／判断链。队列为空不能代替覆盖检查。
2. 先按 `docs/publication.md` 导出私有 release-preview；核对新增、保留和移除 DOI，检查作者、接收稿状态、主题、短说明、Spotlight 与覆盖限制。禁止将意外丢失旧文献当作正常更新。
3. 验证通过后更新唯一 `site/data/` 三文件，执行 `python scripts/publish_snapshot.py --check`、`python scripts/manage_runs.py check-layout`、适用的归档核验、`python -m unittest discover -s tests -v`、`node --check site/app.js`、`node --test tests/test_app.cjs`。失败即停，不跳过校验。抽查网页显示和链接。
4. 暂存前检查全部拟提交文件（包括压缩／归档内容），不得含完整摘要、正文、凭据或私有中转。不提交无关工作区改动。核对远端分支，冲突不能强推或静默合并其他人的工作。
5. 提交推送后跟踪本次 commit 对应的构建和部署，不把上一轮成功当本轮结果。读取正式 HTTPS 页面和数据，与本次产物核对；最终报告提交、部署链接及真实状态。部署失败则报告失败，不能称上线成功。

若本次没有新增／修订文献，不强造网站变化；如需更新覆盖截止时间，也必须通过相同验证。发布证据与本地验收先放 `.private/work/<run-id>/`，不另建公开开发日志。

## 临时材料收尾

按 `docs/repository-layout.md` 的清理规则处理本轮工作目录。导入成功不等于所有输入字段已持久化：核对判断、证据来源和必要书目字段确实进入正式记录；备份则比对恢复来源哈希。可重建预览／导出与独有材料分开，未完成任务保持可恢复，摘要缓存不参与清理。

在当前用户授权涵盖删除时清理已核实目标；否则报告清理建议并请求授权，不从常规发布授权推导删除历史材料的权限。只将有长期价值的精简验收或部署结论留在私有 history，不保留整套临时输出作第二套正式来源。已有正式脚本能完成的工作不要反复新建一次性辅助程序；确有必要时限定在本轮目录。

最终交付补充清理结果：删除和保留数量／体积、未清理原因、恢复入口；如新建 history 记录，计入实际净空间变化。保留项不是新的人工作文献裁决队列，不应冒充科学判断或资料缺口。清理失败或仍有未核实材料时如实说明，不能宣布工作目录已经清空。
